Observatorio Vivo: detectar señales emergentes y conservar su trazabilidad

Observatorio Vivo es un sistema backend local que recopila señales públicas de varias fuentes, extrae y normaliza términos, calcula puntuaciones de actividad, clasifica posibles brotes y mantiene registros que permiten rastrear el origen de las señales.

Código fuente · README principal · Documentación técnica · Archivos del proyecto

Nota de versiones: el README principal identifica la entrega como Observatorio Vivo v0.3.0 y el motor interno como v6.1.2; el README en inglés menciona v6.1.3. Esta ficha evita tratar esos identificadores como una única versión inequívoca. Conviene normalizar el versionado en el repositorio antes de usarlo como referencia de release.

1. Problema y objetivo

Los sistemas de tendencias suelen mostrar rankings de popularidad, pero una posición alta no explica necesariamente si un tema es nuevo, si está acelerándose, si aparece en varias regiones o si la señal proviene de una sola fuente. Observatorio Vivo intenta combinar esas dimensiones para distinguir ruido, primeras apariciones y fenómenos con mayor persistencia o difusión.

Su objetivo es ayudar a investigadores, periodistas y analistas a observar señales públicas tempranas. La puntuación es una heurística de priorización, no una probabilidad calibrada de que un fenómeno vaya a convertirse en tendencia.

2. Fuentes y flujo de datos

El README documenta colectores para Wikipedia Pageviews, Google Trends RSS, Reddit, Mastodon y Hacker News. Según la región elegida, se combinan países e idiomas. Las capturas se ejecutan de forma asíncrona y se registran con fecha, fuente y metadatos.

Fuentes públicas
  → colectores asíncronos (httpx / asyncio)
  → muestras y term_hits
  → normalización, frases y aliases
  → agregación temporal y geográfica
  → detector de brotes / bandeja de observación
  → dashboard, API, informes y alertas opcionales

Las variantes léxicas se pueden asociar a un término canónico mediante aliases, reduciendo la fragmentación de expresiones relacionadas. El sistema también contempla watchlists para seguir temas definidos por el usuario.

3. Scoring y clasificación

La documentación describe un score compuesto que combina novedad temporal, crecimiento, delta entre ejecuciones, cantidad de regiones y fuentes, repetición y cruce entre buckets lingüísticos. En el README principal se enumeran ocho contribuciones y umbrales para cinco estados:

EstadoCondición resumida publicadaLectura
EVENTO3+ regiones, 3+ fuentes, 2+ runs y emergencia ≥70Fenómeno con señales distribuidas y persistentes
PROPAGACIÓN2+ regiones o 3+ fuentes; emergencia ≥52Expansión detectada
BROTE2+ runs, delta positivo y emergencia ≥38Señal temprana repetida
SEMILLAPrimera aparición reciente o un runSeñal inicial, todavía débil
RUIDONo cumple los estados anterioresSeñal insuficiente según las reglas

El README de backend también describe niveles operativos de confianza y alerta: DETECTADO, OBSERVADO y ALERTADO. Son una capa distinta de la clasificación del fenómeno; no deben confundirse con EVENTO/BROTE/SEMILLA. El motor incluye filtros de términos genéricos y cooldown para reducir alertas repetidas.

4. Trazabilidad y almacenamiento

La persistencia usa SQLite con WAL. La documentación identifica tablas para ejecuciones/muestras, apariciones de términos, watchlist, aliases, alertas, bandeja de observación y configuración. El proyecto documenta una vista de origen de señal que permite inspeccionar las apariciones y fuentes que contribuyeron a un término. La trazabilidad es esencial para que el score no se lea como una afirmación sin respaldo.

5. Aplicación y API

El backend utiliza FastAPI y expone una interfaz web local. El README documenta endpoints para salud y estado, ejecutar una captura, consultar términos y brotes, ver el origen de una señal, administrar watchlists y aliases, consultar alertas y exportar JSON/CSV o informes de texto.

6. Instalación y uso

El README principal publica Python 3.8+ y dependencias FastAPI, Uvicorn, HTTPX y Pydantic. El README en inglés enumera Python 3.10+ como requisito, por lo que se debe comprobar la compatibilidad real con el entorno elegido. El arranque documentado es:

git clone https://github.com/Hanzzel-corp/Observatorio.-Vivo.git
cd Observatorio.-Vivo/observatorio_v6_backend
python -m venv .venv
# Activar el entorno virtual
pip install -r requirements.txt
uvicorn app:app --reload --host 127.0.0.1 --port 8765

El repositorio también describe run.sh como método rápido. En Windows, puede ser necesario usar WSL o iniciar Uvicorn directamente desde el entorno Python. Verificar el directorio exacto de backend en la estructura actual antes de ejecutar.

7. Límites y validación pendiente

  • El score es una heurística diseñada por el proyecto; no equivale a una probabilidad predictiva calibrada.
  • Las fuentes públicas tienen sesgos de cobertura, idioma, región, disponibilidad y cambios en sus APIs o feeds.
  • El aumento de menciones o pageviews no demuestra por sí solo causalidad, relevancia social ni persistencia futura.
  • La clasificación depende de ventanas, pesos, alias y umbrales configurados; deben evaluarse con históricos etiquetados.
  • La documentación enumera tests y endpoints, pero esta ficha no afirma una ejecución independiente reciente ni un benchmark externo.
  • La discrepancia de versiones y requisitos entre README ES/EN requiere aclaración en el repositorio.

8. Cómo evaluar el sistema

Una evaluación sólida debería conservar datasets de capturas con timestamp, fijar ventanas temporales, etiquetar eventos de forma independiente y medir precisión, recall, falsos positivos, tiempo de anticipación y estabilidad por región/fuente. También conviene comparar contra baselines simples —por ejemplo, ranking por volumen o crecimiento— para determinar qué aporta el scoring compuesto.

English version · Technical project brief

Live Observatory: emerging-signal detection with source traceability

Live Observatory is a local backend that collects public signals from multiple sources, extracts and normalizes terms, scores activity, classifies potential outbreaks and stores records that help trace signals back to their sources.

Problem and objective

A popularity ranking alone does not explain whether a topic is new, accelerating, appearing across regions or supported by multiple independent sources. The project combines these dimensions to prioritize weak signals and emerging phenomena. Its score is a heuristic for triage, not a calibrated probability that a topic will become a trend.

Architecture and data flow

The repository documents collectors for Wikipedia Pageviews, Google Trends RSS, Reddit, Mastodon and Hacker News. Async collection feeds SQLite records; text normalization, phrase extraction and aliases feed aggregation; the outbreak detector then updates dashboards, reports and optional alerts.

Public sources → async collectors → SQLite samples / term_hits
→ normalization and aliases → temporal/geographic aggregation
→ outbreak detection → dashboard, API, reports and optional alerts

Detection model

The documented score combines recency, growth, score delta, geographic spread, source diversity, repeated observations and cross-language presence. It classifies signals as EVENT, PROPAGATION, OUTBREAK, SEED or NOISE. A separate operational alert layer uses DETECTED, OBSERVED and ALERTED levels. These two classification layers should not be conflated.

Implementation

The backend uses Python, FastAPI, HTTPX and SQLite (WAL). The web dashboard exposes radar, outbreaks, observation, history, watchlist, settings and report views. Documented API operations cover health, state, collection runs, terms, outbreaks, signal origin, alerts and JSON/CSV exports. Telegram notifications are optional.

Version and requirements caveat

The Spanish README labels the release Observatorio Vivo v0.3.0 and the internal engine v6.1.2, while the English README mentions v6.1.3. The two READMEs also differ on the minimum Python version. This page preserves that discrepancy instead of presenting an unverified single release identifier.

Limitations

  • The composite score is a project heuristic, not a calibrated forecast.
  • Public feeds and APIs have coverage, language, regional and availability biases.
  • Attention metrics do not establish causality or future persistence.
  • Weights, aliases, thresholds and time windows affect classifications.
  • This page does not claim a fresh independent test run or external benchmark.

How to evaluate it

A robust evaluation should use timestamped historical captures, independently labeled events, fixed time windows, precision/recall, false-positive rates, lead time and stability by region/source. Compare the composite detector with simple volume- and growth-based baselines.
